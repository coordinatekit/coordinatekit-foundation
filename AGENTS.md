# AGENTS.md

## Repository

coordinatekit-foundation is the base layer CoordinateKit's other repositories build on. Anything more than one repository needs is implemented here once and consumed as a published library, never copied. Ten modules live here, all under the group `org.coordinatekit.foundation`.

`cli-brand` publishes `Banner`, which renders the brand art as a string via `render(boolean ansiEnabled)`. The module depends only on JLine (`implementation`); where the banner prints and the ANSI decision belong to the consumer (README has the recipe). That dependency is the aggregate `org.jline:jline` jar on purpose, not `jline-terminal` plus a chosen provider: it bundles every terminal provider, so JLine selects the one matching the consumer's JDK at run time instead of this module pinning a native backend the consumer should choose. Keep the aggregate.

`conventions` publishes two files and no code: the Eclipse formatter profile and the Apache-2.0 license header. A consumer reads whichever entry it wants out of the jar and wires it into its own Spotless setup, deliberately: the point of that module is that a repository can take one file without adopting a build integration to get it, so it stays plugin-free. README.md has the recipe.

`changelog-gradle` publishes the Gradle plugin under the id `org.coordinatekit.foundation.changelog`, which applies git-changelog (`se.bjurr.gitchangelog.git-changelog-gradle-plugin`) and configures its `gitChangelog` task with CoordinateKit's template, section list, date format, and Handlebars helpers. A consumer's integration is the `plugins` line, `repoUrl` in `gradle.properties`, and an optional `foundationChangelog { fromRevision; initialRelease }` block, and it never writes a `gitChangelog { }` block of its own. The plugin applies git-changelog rather than reacting to it, unlike `concordance-gradle` and Error Prone, so the dependency is `implementation` and reaches the POM. The template is `changelog.hbs` beside the plugin class, with the repository URL and the initial-release text supplied by helpers because the task has no hook for extra template variables. git-changelog's task fails on a template that cannot render but only logs a repository or file error, which leaves the task green and nothing written. The plugin's guard therefore points the task at a file in its temporary directory and moves that file over `CHANGELOG.md` afterwards, failing the build if it is missing, so neither kind of failure touches the old file. Don't go back to deleting `CHANGELOG.md` up front and restoring it in a `doLast`: a thrown failure skips that `doLast` and the file is lost. The helpers and the guard are package-private statics over strings and paths, tested without a template engine or a real build. README.md has the consumer recipe.

`aggregate-javadoc-gradle` and `aggregate-jacoco-gradle` publish one Gradle plugin each, under the ids `org.coordinatekit.foundation.aggregate-javadoc` and `org.coordinatekit.foundation.aggregate-jacoco`. They register the root project's `aggregateJavadoc` and `aggregateJacocoReport` tasks, so a repository takes that wiring as a plugin instead of copying it into its root build, where the copies had drifted. Each adds an extension, `aggregateJavadoc` and `aggregateJacoco`, whose `projects` property defaults to the subprojects that apply `java` or `jacoco`. Neither module depends on anything but the Gradle API and JSpecify, because this repository's own root build compiles their sources through `buildSrc` and applies them from the working tree. README.md has the recipe.

Concordance is the member-order rule this repository's Java conventions state, packaged as three modules. `concordance` publishes the two exemption annotations, `@IntentionalOrder` and `@IgnoreOrder`, and `MemberCategory`; it is the only one a consumer compiles against. `concordance-errorprone` publishes the Error Prone check that enforces the rule, and depends on nothing at run time: it recognises the annotations by fully qualified name through javac's annotation mirrors, so the annotations jar stays on the consumer's compile classpath and off Error Prone's. `concordance-gradle` publishes the Gradle plugin that wires the check in, under the id `org.coordinatekit.foundation.concordance`. The scaffolding field types and lifecycle annotations the check exempts are configuration rather than constants in the checker, so an unconfigured check exempts nothing. README.md has the consumer recipe.

`third-party-licenses-gradle` publishes the Gradle plugin, under the id `org.coordinatekit.foundation.third-party-licenses`, that replaces the hand-copied dependency-license pipeline the `crf` and `coordinatekit` repositories each carry in their `cli/build.gradle`. It applies and configures `com.github.jk1.dependency-license-report` itself, wires `checkLicense` into `check`, and adds a `generateThirdPartyLicenses` task that renders `THIRD-PARTY-LICENSES.txt` and, under `application`, puts it in the main distribution. It ships logic only: the license texts, the allowlist, the normalizer bundle, the overrides, and the copyright notices stay in the consumer, supplied through the `thirdPartyLicenses` extension. The preamble is fixed and says each dependency ships as a separate jar under `lib/`, because `JavaApplication` has no lib-directory setting and the start scripts assume it; its source-availability clause is computed from the `reciprocalLabel`s the consumer registers rather than written out. `excludeBoms` defaults to `false`, as the license report's does. jk1's extension is a set of eager Groovy fields rather than properties, so the plugin copies the extension into it in `afterEvaluate`, and the same hook checks the allowlist against the registered licenses so a mismatch fails before any dependency resolves. jk1's own tasks declare themselves incompatible with the configuration cache, so a build that runs them cannot use it. README.md has the consumer recipe.

`bump-version-gradle` publishes the Gradle plugin under the id `org.coordinatekit.foundation.bump-version` that replaces `scripts/bump-version.sh`, which the CoordinateKit repositories copied between themselves until the copies drifted in their rules and not only their wording. It registers the root project's `bumpVersion` task (group `release`, options `--to` and `--from`) and a `foundationVersion` extension whose only setting is `exclude(String...)`, a list of path globs. The rule set is fixed, the union of the four copies, and every anchor is read from the Gradle model: the root group, the subproject names, and the root project's name. A consumer never writes a rule. A new document format is a pull request to `Rewriter`, and a mention the rules do not recognise fails the bump with its `file:line`, including a second mention on a line where another one was recognised. The module depends on JGit (`implementation`, kept current in the catalog) to list the files Git tracks, found by searching up from the project directory and never through `readEnvironment()`, so a `GIT_DIR` that a hook leaves set cannot redirect it. The task is a thin gatherer over pure package-private deciders, as the Java conventions ask: `Anchors`, `VersionBump`, `Rewriter`, and `BumpPlan` take strings and return strings or throw, `TrackedFiles` is the one class that touches Git, and every refusal happens before the first write. `Rewriter` is built once per bump and holds only the patterns compiled for it. Files are read and written as ISO-8859-1 so that any byte round-trips, which is why `Anchors` re-encodes its names the same way. Release forms (coordinates, jar and archive names, plugin ids, version lines) are rewritten only on a release bump and only on a line showing no `-SNAPSHOT`; snapshot coordinates and the build's own declaration follow every bump; and a form shown at exactly the current `-SNAPSHOT` is caught up on any bump. README.md has the consumer recipe and the full rule table.

## Commands

JDK 21, Gradle 9.7.1 through the wrapper.

```
./gradlew check                 # compile, tests, Error Prone, Spotless check, POM validation
./gradlew test
./gradlew :cli-brand:test --tests '*BannerTest'
./gradlew :cli-brand:test --tests '*BannerTest.markSegments*'   # single test method
./gradlew spotlessApply
./gradlew :concordance-gradle:test --tests '*ConcordancePluginTest'  # runs a real Gradle build
./gradlew :aggregate-javadoc-gradle:test   # runs a real Gradle build
./gradlew :aggregate-jacoco-gradle:test    # runs a real Gradle build
./gradlew :bump-version-gradle:test    # runs a real Gradle build
./gradlew aggregateJacocoReport # build/reports/jacoco/aggregateJacocoReport/html/index.html
./gradlew aggregateJavadoc      # runs with -Werror; any Javadoc warning is a failure
scripts/bump-version.test.sh    # pure bash, no JDK or Gradle
```

Run `pre-commit install` once per clone. The hooks run prettier, `./gradlew spotlessApply`, `scripts/bump-version.test.sh`, and `./gradlew check` before every commit, and enforce Conventional Commits on the message. The `bump-version.test.sh` hook runs only when a staged change touches something under `scripts/`. A commit is slow and arrives pre-verified.

## Build layout

The root `build.gradle` owns all module wiring, and a subproject's own `build.gradle` holds nothing but its `description` and its dependencies. `cli-brand/build.gradle` is five lines. Each plugin module carries one more block, `gradlePlugin { plugins { ... } }`, because a plugin id and its implementation class are that module's identity rather than build wiring, and `java-gradle-plugin` reads them from there to generate the descriptor and the marker publication. The `description` is the one the published POM carries: the subproject's own `build.gradle` has not been evaluated yet when the root's `publishing` block runs, so `description = moduleDescription` in the root's `pom` block reads it through a provider that resolves at POM-generation time rather than reading `project.description` directly; `validatePom` fails `check` if the description, or any other element Central requires, resolves empty, so this workaround cannot silently regress. The wiring comes in two tiers: every subproject gets Spotless, `java-library`, and the Maven Central publishing setup (`maven-publish`, `signing`, `nmcp`, sources/javadoc jars), and `codeProjects`, meaning every subproject except `conventions`, also gets JaCoCo, Error Prone, JSpecify as `api`, and JUnit. `conventions` sits out of the second tier because it has no sources to compile, test, or measure, but it still publishes like any other module.

A new module needs an `include` in `settings.gradle` (which `scripts/bump-version.sh` also reads, to anchor its jar-filename rewrite to this project's own modules), a `nmcpAggregation project(":<module>")` line in the root `build.gradle` so it joins the single Central deployment, and a `build.gradle` setting its `description` and naming its own dependencies. Everything else is inherited. Its package has to be the group plus the module name with dashes turned into dots, so `cli-brand` lives in `org.coordinatekit.foundation.cli.brand`, because the `aggregateJavadoc` plugin derives each module's Javadoc group pattern from its name. Each pattern ends in `*` and javadoc puts a package in the first group that matches it, so the plugin registers the groups longest module name first: without that, `org.coordinatekit.foundation.concordance*` would swallow the errorprone and gradle packages. A name segment whose display form is not the segment capitalised, such as `cli` or `errorprone`, goes in the `wordForms` map of the root `build.gradle`'s `aggregateJavadoc` block.

The repository formats itself against `conventions`' files by path rather than by resolving the published jar, so the build never depends on its own artifact. Consumers use the jar.

Dependency versions live in `gradle/libs.versions.toml`, grouped under comments that state an update policy for each group. The `api` coordinates move conservatively because they are on the published surface, and test dependencies track latest. The `provided` group holds Error Prone and its Gradle plugin at the versions the published check and plugin are compiled against: `compileOnly`, never `api`, since an `api` edge would put Error Prone in the POM and let Gradle upgrade it inside a consumer's build, but updated conservatively because the consumer supplies them at run time and the two modules are binary-coupled to them. The same coordinates appear again, unsuffixed and kept current, in the `build` group, where they run this repository's own linting; that runs the check against a newer Error Prone than it targets, so a routine bump that breaks it fails `check` before any consumer sees it, and the fix is to move the `-target` versions deliberately. The project version lives in `gradle.properties`, and `scripts/bump-version.sh` rewrites it across every tracked file, matching `version=`, `version = "…"`, `<version>…</version>`, `<project>:<module>:<version>` coordinates, and the `id "<plugin id>" version "…"` form a `plugins` block names this repository's own Gradle plugins by. A plugin id shown at the current `-SNAPSHOT` version, as README's aggregate example is, is rewritten by a further rule anchored to that exact version, so the release bump turns it into the release while a snapshot bump leaves it alone; the same rule is why RELEASE.md's "Consuming snapshots" section must never carry a plugin-id example. Two invariants keep the published examples self-maintaining as long as they keep that coordinate form: release coordinates and this project's own module jar filenames (README) track the last release, so a bump to a release version rewrites them and a bump to a `-SNAPSHOT` leaves them alone; snapshot coordinates (RELEASE.md's "Consuming snapshots" section) track the in-development version, so a bump to a `-SNAPSHOT` rewrites that one and a bump to a release leaves it alone. `scripts/bump-version.test.sh` pins both invariants and every error path against throwaway git repositories built with a synthetic group and synthetic module names, so it fails if the script ever stops deriving them from `build.gradle` and `settings.gradle`. That test file and `bump-version-gradle/src/test` are the two paths the script's rewrite excludes: their fixtures and expected-output assertions are version literals that are test data rather than project versions, and a release bump used to rewrite them and break the suite. The first is one exact path, so any other script stays in scope. The second is a directory, because the plugin's fixtures are spread across several files, and its main sources stay in scope. The plugin's own `bumpVersion` task has no such list: it takes `foundationVersion { exclude ... }`, and this repository's root build declares none, so the script is what keeps those literals out of a release bump until it is retired. Keep version literals out of `bump-version.sh` itself for the same reason, comments included, since the script does rewrite its own source.

Error Prone 2.48 needs `-XDaddTypeAnnotationsToSymbol=true` on JDK 21 and `net.ltgt.errorprone` 4.1.0 does not pass it, which is what the `JavaCompile` block in `build.gradle` is for. Removing it breaks compilation.

`concordance-errorprone` is written against javac's own AST and symbol tables, which the `jdk.compiler` module does not export. The `javacExports` list in the root `build.gradle` puts `--add-exports` on that module's compilation and its javadoc, on `aggregateJavadoc` (which reads its sources too), and `--add-exports` plus `--add-opens` on its test JVM, because `CompilationTestHelper` runs javac in process. Nothing else in the repository needs them.

Publishing a Gradle plugin takes two publications rather than one. `java-gradle-plugin` creates `pluginMaven` from `components.java` and a marker publication per plugin id, so the root build registers its own `centralPortal` publication only for modules that do not apply it, and applies the POM metadata, the signing, and `validatePom` to every `MavenPublication` instead of to one by name. Central validates the marker POM by the same rules as any other, and nmcp's aggregation collects both, so the whole deployment still goes up as one bundle. `net.ltgt.gradle:gradle-errorprone-plugin`, git-changelog, and `com.github.jk1:gradle-license-report` publish only to the Gradle Plugin Portal, which is why the plugin modules add `gradlePluginPortal()` as a repository, from the `pluginProjects` block in the root `build.gradle`. The Error Prone dependency is `compileOnly`, so it never reaches the published POM; git-changelog and jk1's plugin are `implementation`, so they do, and a consumer resolves them from the portal too, which is why README's recipe names both repositories. All three plugin modules run real builds through TestKit, so the JaCoCo fixture wiring sits in a `pluginProjects` block in the root `build.gradle`: the instrumented plugin jar, the runtime on the daemon's boot classpath, and the `testKit.fixtureJvmArgs` system property each test's `writeFixture` passes on through the fixture's `gradle.properties`. Only the flatDir check jar and the `concordance.*` properties stay in a `concordance-gradle` block of their own.

`buildSrc` exists so this repository applies its own plugins from the working tree. A plugin resolved from Maven Central would be the last release, and the release pull request has to regenerate `CHANGELOG.md` with the template that pull request ships. `buildSrc/build.gradle` adds `changelog-gradle`'s `src/main/java` and `src/main/resources` as source directories, registers the same plugin id, and reads the same version catalog through `buildSrc/settings.gradle`. The root build applies the changelog plugin by id from its `plugins` block, but the two aggregate plugins by class, so `aggregate-jacoco-gradle` and `aggregate-javadoc-gradle` are compiled in place through `compileJava`'s sources rather than a source set, so IntelliJ does not see duplicate content roots, and are not registered as plugins there. That is why the two aggregate modules' sources may use only the Gradle API and JSpecify, and why no `org.coordinatekit.foundation.concordance` annotations appear in them: `buildSrc` compiles without Concordance's annotations on its classpath. The sources stay in the real modules, so Spotless, Error Prone, Concordance, and the tests still check them there; `buildSrc` only compiles a second copy. Edit the real module, never a copy under `buildSrc`, and keep the two `gradlePlugin` registrations for the changelog plugin in step.

`.gitignore` ignores `*.md` and `.*` wholesale and re-allows a named list, so a new Markdown file or dotfile at the root has to join that list before it can be committed.

## Java conventions

Formatting is Spotless with the Eclipse profile from `conventions`: four spaces, 120 columns for code, 100 for comments, and the license header on every `.java` file. Run `spotlessApply` instead of hand-formatting. A region that has to keep its own shape can be fenced with `// spotless:off` and `// spotless:on`, or with the Eclipse `@formatter:off` tag.

Null safety is JSpecify. `@NullMarked` goes on the package in `package-info.java`, and `@Nullable` marks the exceptions. One package deviates on purpose: `conventions`' `package-info.java` carries no `@NullMarked`, because an annotated package declaration compiles to a `package-info.class`, and that module's jar is meant to hold only its two resources, not a class file. Its own Javadoc says so; don't "fix" it by adding the annotation back. `conventions` is also the one module whose `javadoc` task runs with `failOnError = false`, because javadoc refuses to document a package with no classes to hang it on; a new module inherits every other module's strict default.

Member order is Concordance, the rule this repository also publishes: enum constants, then constants (`static final` fields), then fields, then constructors, then methods, with each category sorted alphabetically and case-insensitively inside itself. Constructors are the one exception, running by ascending parameter count, and static and instance methods sort as one sequence rather than in two blocks. Nested types can sit anywhere in a type, and their own members are checked like any other type's. The root build runs `concordance-errorprone` over this repository's own sources, main and test alike, so a misplaced member fails the build with a message naming both members involved; the one exception is `concordance-errorprone`'s main sources, because nothing can supply the check that compiles it, while its test sources are checked by the module's own freshly compiled check. Test sources are in scope on purpose, which is what the lifecycle-annotation exemption is for, and the `member__scenario` naming carries it: sorting test methods by name groups them by the member under test anyway, and a `@MethodSource` provider and its test share a name, so they compare equal and stay adjacent.

Another order is allowed where it carries meaning, and it is declared rather than merely commented. `@IntentionalOrder(members = {...}, reason = "...")` on a type frees whole categories of its members, as `MemberCategory` uses on its own constants, whose declaration order is the category sequence the rule enforces. `@IgnoreOrder(reason = "...")` on one member takes it out of the check entirely, so the members either side of it compare with each other. Both require a reason. A logger field and a JUnit lifecycle method need neither: the build lists `org.slf4j.Logger` and the four Jupiter lifecycle annotations as exemptions, and the check cannot see them. `Banner.LAYOUTS` needs neither either; its list contents run richest to leanest, which is not a member order at all, and its Javadoc says why.

Javadoc covers private and package-private members too, and `aggregateJavadoc` runs with `-Werror`, so a missing `@param` fails CI.

Banner art belongs in `src/main/resources` as a `.txt` resource rather than in a Java text block: it needs no escaping, diffs as plain text, and art tooling can edit it. Nothing preserves trailing whitespace — Spotless trims it from sources and the pre-commit hook from everything else — so art must never depend on it; padding is applied at render time, as `Banner.rightPad` does.

Code that touches a terminal or the environment splits into a thin private gatherer and a pure package-private decider, so a test can drive the decision with no terminal involved. `Banner.colorMode(boolean, String, Integer, String)`, `Banner.terminalWidth(int, String)`, and `Banner.compose` are the shape to copy.

## Tests

JUnit Jupiter. A parameterized case is a record named `<Something>Parameters` carrying a `name` field, with a `static Stream<…> methodName()` provider directly above the `@MethodSource @ParameterizedTest` of the same name. Test methods are named `member__scenario`, as in `colorMode__ladder`. Bodies are segmented with `// ARRANGE //`, `// ACT //`, and `// ASSERT //`. Assertions describe structure, such as whether the mark is present or which SGR form was emitted, rather than pinning exact art, so the art can be redrawn without rewriting the tests. One exception is deliberate: `BannerTest.mark__widthPinned` pins the mark's width to catch an accidental change to `mark.txt`. The only non-JUnit test is `scripts/bump-version.test.sh`, whose cases are `case_<name>` functions driven by a list at the bottom of the file.

Three suites drive a compiler or a build rather than a class. `ConcordanceTest` compiles fixture sources through Error Prone's `CompilationTestHelper`, marking the line a finding is expected on with a `// BUG: Diagnostic contains:` comment that has to sit directly above the declaration, after any annotation on it. `ConcordancePluginTest` reads the plugin's defaults off a `ProjectBuilder` project and then runs one real Gradle build through TestKit. That build gets both plugins on its own `buildscript` classpath rather than through `GradleRunner.withPluginClasspath()`, which puts the plugin under test in a classloader of its own where it cannot see the Error Prone plugin's types, and it resolves the check from `concordance-errorprone/build/libs` through a `flatDir` repository, so it tests the working tree rather than the last release. `ThirdPartyLicensesPluginTest` does the same with a `ProjectBuilder` project for the defaults, the values copied into jk1's extension, and the allowlist check, and then TestKit builds against a Maven repository the test writes to disk, each module a POM declaring `<licenses>` and a jar built in the test; it needs no `flatDir` because it depends on nothing from this repository at run time. `ChangelogPluginTest` also runs real builds, with the plugin on `GradleRunner.withPluginClasspath()` because git-changelog is applied by the plugin itself and needs no other plugin's types. Its fixture is one directory that is both the Gradle project and the git repository, and JGit writes the history with pinned dates at noon UTC so the rendered headings do not depend on the daemon's time zone. The `v0.1.0` tag sits above a first commit rather than on the root commit, because git-changelog includes a parentless `fromRevision` commit even though the lower bound is otherwise exclusive.

`AggregateJavadocPluginTest` and `AggregateJacocoPluginTest` follow the same split: defaults and task configuration from a `ProjectBuilder` project, then one TestKit build each. Those builds use `withPluginClasspath()` and a `plugins { id ... }` block, which Concordance's cannot because it needs Error Prone's types, so they also exercise the generated plugin descriptor. The Javadoc build asserts that each module's packages land under its own tab and that a dependency outside the selection is built but not documented, and the JaCoCo build reads the XML report to check that every selected module has covered lines and an unselected one is absent. Every TestKit fixture writes the `testKit.fixtureJvmArgs` system property, which the root build sets on each plugin module's `test` task, into its `gradle.properties` as `org.gradle.jvmargs`, so the coverage of the fixture builds reaches the module's report.

`bump-version-gradle` splits its tests by how much of a build they need. `RewriterTest`, `VersionBumpTest`, `AnchorsTest`, and `BumpPlanTest` run on strings alone, with synthetic anchors (the group `com.example.widgets`, the root `widgets`, and the modules `alpha-core`, `beta`, and `delta`) and ordinary versions, because foundation's own release bump excludes `bump-version-gradle/src/test` along with the bash test file. `RewriterTest.rewrite__repositoryDocs` is the one exception: it reads this repository's real `README.md` and `RELEASE.md` through the `bumpVersion.*` system properties that the root build sets from the Gradle model, so no foundation literal sits in a test source, and it takes the place of the bash `real_repo_*` cases. `TrackedFilesTest` builds real repositories with JGit, including a hand-written linked worktree and an index with conflict stages. `BumpVersionPluginTest` reads the wiring off a `ProjectBuilder` project and then runs TestKit builds against throwaway repositories in the three shapes the consuming repositories have, with the version in `gradle.properties` beside several modules, in `build.gradle`, and in a single project documented by its archive and version line. Those builds use `withPluginClasspath()`, put a decoy `GIT_DIR` in the environment to show it is ignored, check that a refused bump leaves every file byte for byte, and run twice under the configuration cache, restoring the bytes between runs because the bump itself changes `gradle.properties`, an input of the cache entry.

## CI and releases

Pull requests run tests with a JaCoCo coverage comment, Javadoc, and Spotless. Every workflow is filtered by path to the concern it covers, so `scripts/bump-version.test.sh` runs from its own `scripts.yml` rather than from `test.yml`: it needs neither a JDK nor Gradle, and folding it into the Java job would make a scripts-only pull request pay for a full Gradle run it cannot affect. The Spotless job applies formatting and pushes a `style:` commit on same-repo pull requests, and only checks on forks. Pull request titles are linted as Conventional Commits with a lowercase subject.

Releasing takes two steps. The Prepare Release workflow, dispatched manually with a version, opens a `chore: prepare release <version>` pull request; pushing the `v<version>` tag afterwards publishes every module to Maven Central and only then cuts the GitHub release from the matching `CHANGELOG.md` section. `RELEASE.md` has the full flow, the credentials, the snapshot path, and the bump back to the next `-SNAPSHOT`.

Three facts about publishing matter while editing the build. The `nmcp` aggregation plugin collects every module's publications into one bundle and uploads it once, so Central validates and publishes them as a unit rather than as independent deployments. Deployment runs with `publishingType = "AUTOMATIC"` straight to `central.sonatype.com`, so a tag push goes live with no Portal click and no undo. Signing is gated on `isPublishingToCentral`, true only when `nmcpPublishAggregationToCentralPortal` is in the task graph, so `./gradlew build`, `publishToMavenLocal`, and snapshot uploads all run without a GPG key.
